# OntoQuery 演示讲解词

作者：月夜烛峰

版本：1.0.0

面向讲解人的按页演示脚本。文中引用数字均为 2026-10-08 实测（基准 run 8 为传统侧 Mock、run 9 为真实 LLM、核心问题实时执行）；现场演示时以页面实时数字为准——本系统没有写死任何结果数字。

## 演示前准备（1 分钟）

1. 确认数据库已按 README 初始化、应用运行在 http://localhost:8080。
2. 演示前重置 LLM 缓存：`POST /api/meta/llm-cache/clear`（或点顶栏 LLM 状态芯片右侧的清空按钮，仅缓存非空时出现），避免"LLM 缓存命中"徽标混淆首轮讲解。
3. 确认传统侧模式徽标：
   - 配置了 local.yml 密钥 -> 紫"LLM: deepseek-flash"（真实调用，单题 10 到 30 秒）；
   - 未配置 -> 琥珀"模拟模式（降级）"（确定性缺陷生成器，秒级）。
   两种模式都是真实演示素材，讲解词分别见下文。

## 开场（30 秒）

> 这是同一个自然语言问题、两种技术路线的对照实验。左边把领域知识建成轻量本体，用确定性推理生成 SQL，每一步可审计；右边是主流做法——把表结构喂给大模型直接生成 SQL。两边连同一个数据库、走同一个只读执行器，数字都是真查出来的。今天看四件事：准不准、为什么错、能不能解释、贵不贵。

## 第一页 对比问答（3 分钟，核心）

输入核心演示问题（建议芯片第一个）：

> 近一个月诊断为2型糖尿病且HbA1c大于7的患者中，使用二甲双胍治疗的有多少人？

讲解顺序（自上而下）：

1. **五步轨迹**：点开左侧"本体推理"步骤——看到同义归一（HbA1c -> LAB_HBA1C）、时间挂靠（"近一个月"挂 diagnosis_date，并明确列出"未挂到 test_date / prescribe_date 及距离理由"）、值域校验（HbA1c 正常 4~6、可信 3~20，阈值 7 合法）。这就是可解释性：每个决策有规则依据。
2. **SQL 块**：左侧三个独立 EXISTS 子查询，各管一个约束。话术：EXISTS 天然免疫 JOIN 扇出——患者对诊断是一对多，JOIN 后 COUNT 行数会翻倍，这是传统路线最常见的暗坑。
3. **结果与置信度**：本体侧 533 人、总耗时 24 毫秒、置信度 98（扣分因子逐条列出：同义词实体得分 0.9425 扣 2 分，无歧义、无执行计划警告）。
4. **右侧对照**（分两种情况）：
   - **真实 LLM 模式**：DeepSeek 也给出 533（这道题它做对了），但耗时 18.7 秒、置信度 97（值域知识未参与扣 3 分）。话术：大模型在简单题上能力已经不错，问题是每题近 20 秒的延迟、token 成本、以及无法说明"为什么这样查"——点开右侧步骤，只有一坨 DDL 加一段生成文本，没有决策依据。
   - **模拟模式**：右侧数字必然不同（如 44 对 265、0 对 2000），展开"风险检测"面板逐条看实锤（下文"右侧数字为何错"）。
5. **安全彩蛋**（可选）：输入"删除患者表"——右侧拒绝执行并给出解释，左侧退化为无害计数 SELECT。所有 SQL 只经 SafeQueryExecutor 白名单（单条 SELECT、10 秒超时、500 行上限），两侧都不可能写库。

### 右侧数字为何错（模拟模式实锤）

数据里的陷阱是真实埋设的（事实表 code 列恒定标准、name 列按行散布多写法），模拟模式把"典型 NL2SQL 缺陷"确定性地演出来：

| 现象（基准实测） | 根因 | 数据实锤 |
|---|---|---|
| 问"II型糖尿病（含糖尿病II型、成人糖尿病等写法）有多少患者"，答 0（正确 2000） | LIKE 用户原词字面匹配 | fact_diagnosis 中 E11 共 2000 行，4 种写法各 500 行；LIKE '%2型糖尿病%' 只命中 500 行，漏配 1500 行（75%） |
| 问"近三个月诊断且 HbA1c 大于 8 且二甲双胍"，答 44（正确 265） | LIKE 原词 + LEFT JOIN 链 + COUNT(*) 未去重 | 同义词漏配与 JOIN 扇出叠加，偏差数倍 |
| 问"近一个月新增诊断记录多少条"，答 20000（正确 6495） | 时间条件整体丢失，退化成数患者总数 | 三条事实表各带独立日期列，时间词不挂列就等于没问 |
| 问"E10 至 E14 前五种编码及条数"，答错并列段 | 并列无确定性次序（黄金侧已修正为 cnt DESC 再按编码排序） | 排名题必须在并列时给出确定性 tie-break |

话术总结：**这些不是 bug，是"没有本体"的必然结果**——字面匹配不知道"格华止就是二甲双胍"，表结构里也没有一行注释能告诉你"近一个月修饰的是诊断日期"。

## 第二页 本体问数 / 第三页 传统问数（各 1 分钟）

- 本体问数页：再演示两三个变形问题——"使用格华止治疗的患者有多少人"（同义词归一，SQL 与标准名完全一致）、"HbA1c 大于 70 的患者"（值域校验警告：超出可信区间 3~20，疑似单位错误）、"各区域有多少患者"（分组意图）。超纲问题如实报错，不硬编。
- 传统问数页：同一个问题单独跑右侧，展示模式徽标与风险面板；真实 LLM 模式下可现场感受延迟。

## 第四页 本体图谱（1 分钟）

> 本体不是黑盒，它本身就是资产。

三栏：类树（真实实例数徽标）-> 点"糖尿病类"（E10 至 E14 五个实例，子类闭包展开的依据）-> 点 E11：右侧看到 4 个同义词、映射芯片 fact_diagnosis.disease_code = 'E11'。话术：业务方在这里维护同义词与层级，改一行元数据，查询口径立刻全站生效——这是本体路线的运维逻辑。

## 第五页 语义解析过程（1 分钟）

最近一次对比的双侧轨迹逐项对照。重点展示左侧时间挂靠的"未选中分支说明"（未挂到 test_date：距离远于诊断词）与右侧的 DDL 原文——同一道题，一边是决策树，一边是掷骰子。

## 第六页 对比分析（2 分钟）

先跑基准（对比分析页按钮，或 `POST /api/benchmark/run?forceMock=true`，Mock 模式秒级）：

- 36 题六类目实测（run 8，传统侧 Mock）：本体 36/36（100%），传统 Mock 2/36（6%）；本体总耗时 383 毫秒对 Mock 2222 毫秒。
- 逐类目讲：简单单表双方都能对；两表关联开始拉开；多表复杂、同义词理解、时间修饰歧义、多层推理四个类目 Mock 全军覆没——每一类都对应第一页讲过的一种缺陷。
- 真实 LLM 基准实测（run 9，deepseek-flash 串行真实调用）：传统侧 18/36（50%），总耗时 148.8 秒；本体侧仍 36/36、466 毫秒。真实失败模式有讲解价值：列表题只返回首个元素或用名称不用标准码（问前五科室只答一个科室），数字题口径漂移（"近一个月新增诊断记录"答 5850 对 6495——时间窗理解不一致），多约束题漏条件（"肌酐检验的慢肾病患者"答 70 对 36）。
- 如需现场重跑真实 LLM 基准：`POST /api/benchmark/run`（不带参数，串行真实调用约 2 到 10 分钟，受缓存影响，演示前预先跑好）。

指标卡下方的 12 维度定性表按需讲 3 个：可解释性、运维方式（改本体元数据对重新调 prompt）、成本（零 token 对每题一次调用）。

## 常见提问（FAQ）

- **"真实大模型有这么差吗？"** 模拟模式展示的是缺陷形态，不是大模型水平。真实 deepseek-flash 全量基准实测 18/36（50%）：单表计数与两表简单条件多数能对，但列表题常只回首个元素或用名称不用标准码、时间窗与多约束题口径漂移；核心题它答对了（533），但单题 18.7 秒、每题一次 API 成本、无法解释决策过程。本体侧同基准 36/36、总耗时 466 毫秒、零 token 成本、每步有规则依据。
- **"本体侧为什么能全对？"** 因为 36 道题在本体覆盖的意图与词表之内；超纲问题（如"平均年龄是多少"）会诚实返回"无法解析"。本体的上限是词表与规则的质量，但错误可定位、可修正——修正一行映射立即生效。
- **"两侧会不会都能改库？"** 不会。SafeQueryExecutor 是唯一 SQL 出口，白名单只放行单条 SELECT/WITH，DML/DDL 关键字直接拒绝（有单测覆盖堆叠注入、注释伪装、字符串字面量豁免等边界）。
- **"数据是真的吗？"** 是确定性合成的（重跑逐位一致），规模 2 万患者、31 万条事实记录；陷阱（写法散布、独立日期列）是故意埋的，但两侧数字都是对这份真实数据查询出来的。
